# 실시간 실행 측정

## 재현

box/에서 PowerShell로 다음 명령을 실행한다. 실제 회원 DB 대신 임시 테스트 DB와 합성 계정을 사용한다.

```powershell
$env:BOXING_COACH_PYTHON=(Resolve-Path .venv/Scripts/python.exe).Path
$env:BOXING_COACH_PERFORMANCE_SECONDS='60'
& ../.tools/node-v22.20.0-win-x64/node.exe tests/test_session_browser.js
```

성능 모드는 640×360, 30FPS 목표의 움직이는 캔버스 스트림을 실시간 생성한다. 실제 앱의 Worker 모델 추론, 점수 보고서 저장, 녹화 동시 실행, 종료 팝업을 사용한다. 실제 카메라 하드웨어나 사람의 펀치 인식 정확도를 검증하지 않는다. 사용자 지시에 따라 녹화본 재생 검증은 수행하지 않는다. 성능 측정에서만 라운드 제한을 측정 길이+30초로 설정하며 제품 설정/DB는 변경하지 않는다.

## 60초 결과 (2026-09-22)

- Chrome 153.0.8010.50, MediaPipe Pose Lite CPU Worker, 기본 앱 녹화 설정.
- 60.072초 동안 표시 콜백 1802회(약 30.0FPS), 분석 1185회(약 19.7FPS).
- 추론 중앙값 43.2ms, p95 46.8ms, 프레임 제출 시각→결과 수신 p95 47.6ms.
- 10초 간격 모든 표본에서 녹화 활성. 오류 메시지 0건. 종료 후 보고서 저장/팝업 성공.
- 렌더러 JS heap 표본 약 2.97~4.73MB. 전체 앱 메모리/Worker WASM/GPU 메모리가 아니므로 메모리 누수 없음의 증거로 사용하지 않는다.
- 원시 결과: `artifacts/session-performance-1790037059710.json`(Git 제외).

분석 20FPS 목표에는 약간 미달한다. 관절이 검출되지 않는 입력 경로의 측정이며, 사람을 추적하는 성능이나 펀치 완료→피드백 지연으로 해석하지 않는다. 실제 기기에서 렉이 없다고 보장하지 않는다.

## 5분 연속 결과 (2026-09-22)

같은 설정으로 300.390초 동안 표시 9011회(30.0FPS), 분석5974회(19.9FPS), 추론 중앙값43.4ms/p95 46.1ms, 결과 수신 p95 46.8ms를 기록했다. 30개 표본에서 녹화 활성과 분석 결과 증가가 유지됐고 Worker 오류는 0건이다. 렌더러 JS heap은 첫 표본4.67MB, 마지막3.17MB로 표본상 누적 증가를 보이지 않았다. 이는 Worker/GPU 메모리 검사나 수시간 안정성 증명이 아니다. 원시 결과는 `artifacts/session-performance-1790037147132.json`이다.

## 자원 및 기준선 비교

2026-09-22 별도 30초 요청 측정에서 Windows 카운터를 함께 수집했다. 카운터 조회 지연을 포함해 실제 경과는 요청보다 길며 순수 지연 벤치마크와 분리한다. 분석 켠 결과는 `session-performance-1790075258765.json`, 끈 결과는 `session-performance-1790075321104.json`이다. 모든 파일은 artifacts/에 있다.

| 지표 | 분석+녹화 | 녹화 기준선 |
|---|---:|---:|
| 표시 FPS | 30.01 | 29.98 |
| 브라우저 프로세스군 CPU 초/실제 초 | 1.22 | 0.35 |
| Private bytes 표본 | 544~548 MB | 397~448 MB |
| Working set 합 표본 | 873~875 MB | 719~758 MB |
| 해당 Chrome GPU 3D 엔진 표본 | 18~19% | 7~10% |

CPU 1.22는 논리 코어 1개의 122%에 해당하는 프로세스 합산 시간이며 전체 20논리 코어 CPU 사용률로 단정하지 않는다. Working set 합에는 공유 페이지 중복이 있을 수 있다. GPU 수치는 개별 엔진 순간 표본이며 GPU 전체 점유율이 아니다. 첫 분석 표본의 Windows 카운터는 시간 초과로 누락됐다. 물리 카메라·인체 검출 입력·다른 PC·수시간 사용의 성능으로 일반화하지 않는다.

## Chrome 합성 카메라 제한

`--use-fake-device-for-media-stream`의 스트림이 앱·모델 없는 빈 페이지에서도 getUserMedia 직후 live에서 약 1초 내 ended로 전환되는 현상을 확인했다. 앱에서 모델을 비활성화해도 동일하며, 시작 재시도에서 Requested device not found가 나타난다. 이 환경에서는 해당 합성 장치로 카메라 하드웨어 안정성 결론을 내릴 수 없다. 캔버스 스트림 성능 모드와 구분한다. 원인을 제품 코드 결함으로 단정하거나 테스트 통과를 위해 실제 제품의 카메라 입력을 대체하지 않았다.
