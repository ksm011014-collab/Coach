## 실행 계획

1. 실제 PC에서 MoveNet Lightning과 MediaPipe Pose Lite의 런타임·지연·정확도 비교 도구 준비.
2. 로컬 추론과 시간 기반 동작 이벤트 분리, 좌우/스탠스/가림 처리 및 평가 자료 준비.
3. 점수·5초 피드백·라운드 저장을 SQLite/Supabase 권한 계약에 연결.
4. 명시적 채팅 종료가 있는 홀로그램/대화 팝업과 무료 서비스 어댑터 구현.
5. 실제 카메라·라벨 영상·녹화 동시 성능·회귀·staging 검증 후 인수인계.

## 확인한 환경

- Intel Core i5-13500HX, 14코어/20논리 프로세서.
- 약 16 GB RAM, Intel UHD 및 RTX 4060 Laptop GPU. 실제 추론 장치는 별도 측정한다.
- 라운드 타이머는 stopSession('timer')을 호출한다. 저장 후 팝업에서 채팅 종료를 누르고 다음/종료를 선택하며 대화 시간은 다음 라운드에 포함하지 않는다.
- Python 분석 capability는 not_installed이지만 브라우저 Worker는 별도로 실행한다. 세션에는 시간/녹화와 버전 1 점수·동작·가드·추적 구간 보고서를 기록한다.
- 기존 Python 101개 및 관리/세션 회귀 통과 기록을 기준선으로 사용한다.

## 모델 비교 원칙

### 시험 모델 설치 재현

box/에서 먼저 `npm install --prefix artifacts/pose-benchmark --ignore-scripts --no-audit --no-fund @mediapipe/tasks-vision@0.10.22-rc.20250304`를 실행한 다음 `.venv/Scripts/python.exe tools/prepare_motion_assets.py --download`를 실행한다. 다운로드 없는 재준비는 `--download`를 생략한다. npm 런타임과 모델은 앱 코드와 분리해 Git 제외 경로에 둔다.

준비 도구는 runtime 버전, Apache-2.0 패키지 메타데이터, Pose Lite 고정 SHA-256을 확인한 뒤 앱의 `web/vendor/motion/`에 복사한다. 원본 README/MediaPipe LICENSE와 각 설치 파일의 크기·SHA-256·출처를 manifest에 남긴다. 현재 설치는 9개 파일, 25,368,518바이트이며 압축 배포 크기는 아니다. 원본 코드는 변경하지 않는다. [MediaPipe 공식 라이선스](https://github.com/google-ai-edge/mediapipe/blob/master/LICENSE) 및 [모델 안내](https://developers.google.com/edge/mediapipe/solutions/vision/pose_landmarker)를 따른다. 시험 모델의 최종 정확도 검증을 대신하지 않는다.

### 저장 기능 호환성

`GET /api/system/health`의 `capabilities.motion_reports.versions`에 1이 있는 서버만 버전 1 점수 보고서 저장 지원으로 취급한다. 기존 엔진과 Android 오프라인 구현처럼 필드가 없으면 운동 시간/녹화 기능을 유지하되 동작 점수 저장 미지원과 업데이트 필요를 표시한다. 기존 `analysis`는 Python 서버 추론의 미설치 상태이며 브라우저 Worker와 별개다. WPF 브리지 프로토콜은 변경하지 않았다. 로컬 설치에는 새 Python worker와 웹/모델 파일이 필요하고, 중앙 서비스에는 새 서버 capability 및 staging에서 검증한 RPC가 필요하다. Android 오프라인 동작 점수 저장은 지원 확인하지 않았다.

MoveNet Lightning은 저지연 후보이며 MediaPipe Lite는 추정 깊이와 33개 관절을 활용할 수 있는 후보다. 깊이 출력은 단안 추정이며 측정된 깊이로 취급하지 않는다. 모델 이름만으로 복싱 정확도를 보장하지 않는다. YOLO는 성능 외에도 배포 라이선스를 검토해야 하므로 우선 도입하지 않는다.

MediaPipe 동기 추론은 메인 스레드를 막을 수 있으므로 Worker에서 비교한다. 카메라 프레임은 로컬 메모리에서 처리하고 한 번에 하나만 추론한다. WebGL/CPU 실제 선택, 준비 시간과 안정 상태 지연을 구분한다. 합성 이미지/영상 속도 측정은 실제 섀도복싱 정확도 검증이 아니다.

## 제안하는 검증 기준

초기 목표이며 실제 장치·영상 결과와 함께 검토한다. 녹화 동시 카메라 표시 30 FPS 목표, 분석 20 FPS 이상 목표, 처리 대기열 최대 1개, 추론 p95 50ms 이하 목표. 동작 완료 후 결과 표시는 회수·원투 연결 대기 시간을 별도로 기록한다. 라벨 평가에서는 동작별 정밀도 95% 이상, 재현율 90% 이상, 비동작 오탐 분당 1회 이하를 목표로 한다. 미달 결과는 감추지 않고 미검증/미달로 기록한다.

정면/얕은 대각선, 양 스탠스, 단발/연속/비동작/가림을 분리한다. 조정용과 최종 평가 영상을 분리하며 사용자가 촬영한 자료는 Git 제외 위치에서만 처리한다. 원본 전송 없이 필요한 라운드 요약만 챗봇에 연결한다.

## 초기 실행 측정

tools/benchmark_pose.cjs로 Chrome headless에서 빈 640×480 캔버스를 입력해 준비 10회 이후 120회 추론을 측정했다. 카메라·인체 영상·녹화·Worker를 포함하지 않은 로딩/실행 확인이며 모델 선정 근거로는 불충분하다. 실제 WebGL renderer는 RTX가 아닌 Intel UHD였다.

| 후보 | 추론 중앙값 | p95 |
|---|---:|---:|
| MoveNet Lightning/WebGL | 27.7 ms | 32.7 ms |
| MediaPipe Lite/CPU | 75.3 ms | 84.0 ms |
| MediaPipe Lite/GPU | 30.0 ms | 33.5 ms |

빈 화면에서는 MediaPipe의 사람 검출 실패 경로만 실행될 수 있으므로 인체 검출/추적 경로와 직접 비교하지 않는다. MoveNet의 posesDetected는 반환된 후보 수이며 신뢰도를 통과한 사람 수가 아니다. 원시 측정은 Git 제외 artifacts/pose-benchmark/smoke-results.json에 있다. 패키지는 해당 폴더에만 설치하여 앱 의존성을 바꾸지 않았다.

현재 구현 모델은 MediaPipe Pose Landmarker Lite, CPU Worker로 선정했다. 단안 추정 깊이와 복수 사람 보류에 필요한 출력을 제공하며, 현재 PC의 5분 실시간 생성 입력에서 화면 30FPS/분석 약20FPS를 유지했다. MoveNet Lightning은 비교 후보로 보존하지만 현재 깊이 기반 판정 어댑터와 복수 사람 보호를 충족하지 않아 제품 기본값으로 사용하지 않는다. GPU가 단독 추론에서 빨랐지만 앱 동시 실행의 장기 근거가 CPU보다 부족해 기본으로 선택하지 않았다. 이는 실제 펀치 정확도 검증을 마친 모델이라는 의미가 아니다.

### Worker 연결 진행

motion-pipeline.mjs는 준비 완료 후 하나의 캡처/추론만 허용하고 중간 프레임을 버린다. 세대 번호로 종료 후 늦은 응답을 무시하며 응답 시간 초과 시 Worker를 종료한다. motion-worker.js는 같은 서버의 모델/런타임만 읽고 전송된 비트맵을 처리 후 해제한다. 앱 카메라와 세션에 연결했다.

실제 Chrome Worker에서 MediaPipe Lite GPU 빈 화면 60회 추론을 완료했다. 안정 구간 중앙값 31.4ms, p95 41.2ms, 전송 포함 p95 41.7ms였다. 메인 화면 animation callback도 진행했다. 이 측정은 실제 사람/녹화/장시간 부하 검증이 아니다. 최초 GPU 준비가 5초를 넘겨, 준비 완료 알림 전에 워밍업하도록 수정했다. 다른 사람 감지는 MediaPipe numPoses=2 후보만 가능하며 MoveNet singlepose에는 별도 보호가 필요하다.

test_motion_pipeline.mjs는 대기열 억제·캡처 중 종료·오래된 응답·중복 응답·시간 초과·프레임 해제를 검증한다. 모델 정확도 검사가 아니다.

### 스켈레톤과 녹화 동시 실행

motion-session.js를 카메라 시작/종료에 연결했다. 입력은 가로 최대 640px로 축소하며 원본 녹화 스트림은 유지한다. motion-skeleton.mjs는 좌우 반전·object-fit cover 크롭·화면 크기를 반영하고 낮은 신뢰도 관절, 복수 사람, 250ms 이상 오래된 결과를 그리지 않는다. 관련 좌표/만료 단위 검사가 통과했다. 시험 동작 분류·점수도 라운드에 연결했다.

Chrome 합성 카메라와 기본 MP4 코덱의 동시 검사에서 GPU delegate 사용 시 최초 또는 재시작 녹화 chunk 대기가 시간 초과됐다. CPU delegate에서는 녹화·재시작·중단/재시도 구간이 진행됐다. 따라서 현재 생성 자산은 임시 CPU 설정이며 성능 기준 달성/최종 모델 선정이 아니다. GPU 단독 추론 수치로 녹화 병행 성능을 대신하지 않는다. 공식 런타임이 console.error로 출력하는 정확한 XNNPACK INFO 문구만 회귀 오류 수집에서 제외하고 실제 오류는 유지한다.

prepare_motion_assets.py는 비교 폴더의 고정 런타임과 SHA256 검증 모델을 Git 제외 web/vendor/motion에 준비한다. 배포 자산/라이선스 패키징과 모델 없는 환경의 지원 흐름은 추가 작업이다. 현재 웹은 0.8.0-dev.1이며 개발 버전이다.

## 무료 서비스 상태

## 동작 판정 모듈 진행

motion-features.mjs는 MediaPipe의 영상/추정 world 관절을 검증하고 어깨 폭으로 정규화한 손목 상대 위치·팔꿈치 각도·가드 여부를 만든다. 낮은 신뢰도, 가림, 겹친 손, 불안정한 신체 크기, 복수 사람 또는 사람 수 확인 불가를 거부한다. 카메라 좌표계의 상대 특징이며 시점 불변을 보장하지 않는다. MoveNet은 깊이/복수 사람 보호가 없는 상태에서 동작 평가를 활성화하지 않는다.

motion-recognizer.mjs는 250ms 가드 준비→최소 변위→시간 궤적→가드 회수 후 판정한다. 250ms 이상의 관측 단절, 1.8초 초과 동작, 애매한 방향은 초기화/미판정한다. 스트레이트·수직 상승·수평 궤적과 팔꿈치 조건은 실제 영상 조정 전의 시험 규칙이다. 잽은 원투 연결을 기다리고 완성된 원투는 구성 펀치를 중복 발행하지 않는다. 단독 뒷손 스트레이트는 현재 사용자 표시 대상이 아니다.

시험 수행 품질은 팔꿈치 형태 40%, 반대손 가드 관측 비율 30%, 회수 30%로 계산한다. 관절 visibility 최소값은 추적 신뢰도이며 분류 확률이 아니다. 점수는 동작당 최대 10, 원투는 두 동작 평균 품질에 따른 단발 점수의 두 배다. 이 산식은 코칭 타당성 검증 전이며 시험 상태로 세션 점수/저장에 연결했다.

합성 궤적의 분류·모호한 움직임 거부·좌우 스탠스·원투 중복 억제·준비/회수 전체 흐름·정지/추적 상실 검사가 통과했다. 실제 펀치 정밀도/재현율은 미측정이다. 해당 모듈은 실제 영상 평가 후 운영 사용 기준을 확정해야 한다.

## 무료 서비스 연결 진행

피드백 설정은 `motionFeedback`으로 장치 설정에 보관하며 기본은 5초 요약이다. 동작별 시험 모드는 다음 라운드부터 적용하고 1초 안의 연속 이벤트는 가장 최근 것만 표시하여 대기열을 만들지 않는다. 반대손 가드 관측 비율이 모든 대상 동작에서 90% 이상이면 유지 안내, 요약에 50% 미만인 동작이 두 번 이상 관측되면 가드 확인 안내를 제공한다. 단일 저품질 수치로 자세를 단정하지 않는다. 실제 판정 안정성이 검증되지 않았으므로 동작별 피드백을 기본값으로 바꾸지 않는다. 가드 관측 근거와 추적 공백을 라운드 JSON에 저장·재조회하며 [코치 계약](09-coach-service.md), [추적 보고서](11-tracking-evidence.md)를 따른다.

## 라운드 저장 계약 진행

로컬 PATCH /api/sessions/{id}/end에 선택적 motion_report를 추가했다. 기존 시간/녹화 전용 요청은 그대로 지원한다. 기존 feedback_report JSON 텍스트에 정규화한 이벤트/횟수/total_points/mean_quality를 저장하여 현재 SQLite schema 3을 변경하지 않는다. overall_score는 종전 0~100 의미를 유지하도록 평균 수행 품질을 저장하고 누적 점수와 분리한다. 실제 개발 DB 데이터는 이 구현 검사로 변경하지 않았다.

서버는 버전·스탠스·완료 시점·이벤트 ID·동일 손 중복·신뢰도·점수 범위를 검증한다. 반대손의 시간 겹침은 허용하되 원투와 구성 이벤트 중복은 거부한다. 점수는 품질 10점당 반올림, 최소 1점·최대 10점이며 원투는 두 배다. 이 규칙으로 클라이언트 총점 입력을 무시하고 합산한다. 품질은 장치 추정값이며 서버가 원본 영상으로 검증한 값이 아니다.

현재 계정 상태/권한을 다시 읽고 종료 시각·결과·감사를 같은 트랜잭션으로 저장한다. 동일 결과 재시도는 기존 결과를 반환하며 변경된 최종 결과는 409다. 미연결/이벤트 없음의 mean_quality는 null이다. 로컬 권한/충돌/중복/잘못된 값 검사는 통과했다. Supabase `finish_motion_round`와 프론트 전송을 연결했다. 202609210001 마이그레이션을 staging에 적용하고 실제 합성 Auth 계정으로 저장/재조회, 재계산, 동일 재시도, 변경 거부, 감사 단일 생성, 다른 센터/플랫폼 관리자 변경 거부를 확인했다. 운영 배포는 하지 않았다.

### 실시간 라운드 연결 (2026-09-21)

`motion-round.mjs`는 실제 세션 시작 후의 좌표만 판정한다. 라운드마다 새 판정기와 0점으로 시작하며 성립한 이벤트의 ID/손/시간 중복을 걸러낸다. 시간은 라운드 상대 정수 밀리초로 저장한다. 종료 시 보고서 스냅샷을 고정하고 저장 재시도에서 같은 보고서를 보낸다. 우측 점수와 좌측 하단 감지/가드 요약, 피드백 모드 설정, 종료 팝업의 저장된 횟수/누적 점수/평균 품질을 연결했다. 판정은 명시적으로 시험 상태이고 실제 정확도 검증 전이다. 종료 요약 근거 확장은 [인수 점검](10-motion-acceptance.md)의 남은 작업이다.

원투의 뒷손이 연결 시간 안에 시작했으면 회수 완료를 기다리고 잽을 먼저 확정하지 않도록 수정했다. 추적이 끊겨도 이미 완료한 잽은 보존하고 진행 중 궤적만 폐기한다. 합성 규칙/라운드 검사로 점수 초기화·중복 방지·보고서 재시도·무관측 무평가를 확인했다. 실제 영상의 인식 성능 증거가 아니다.

### 라운드 종료 팝업 진행

2026-09-22 종료 흐름 보완: 최초 종료 요청에서 전송 보고서·수동/타이머 종료 사유·장치 종료 시각을 고정한다. 실패 후 재시도에도 같은 보고서를 보내고 화면 운동 타이머를 늘리지 않는다. 분석 결과 생성 실패와 녹화 종료 실패는 각각 안내하되 운동 기록 종료 요청을 계속한다. 팝업/코치 요약은 저장된 보고서의 실제 수행 시간을 우선하여 저장 재시도 대기를 운동 시간으로 설명하지 않는다. 종료 사유는 현재 팝업 전환용 메모리 상태이며 DB 영구 필드는 아니다. 기존 설정은 라운드 길이만 있고 휴식 카운트다운은 없으므로, 저장→대화→명시적 다음/종료 선택→새 라운드 시작 순서를 사용한다.

round-coach.js와 round-coach.css를 추가하고 서버의 세션 종료 저장 성공 후 팝업을 연다. 현재 기존 데이터 모델의 세션 한 건이 한 라운드에 해당하며 다음 라운드는 새 세션을 생성한다. 운동 묶음/라운드별 분석 저장 계약은 추가 구현 대상이다. 표시 시간은 저장된 시작/종료 시각으로 계산한다.

팝업은 Escape로 자동 종료되지 않고 ‘채팅 종료’ 후 다음 라운드/세션 종료 선택을 제공한다. 대화 중 새 세션 시작을 차단하며 저장 실패에서는 팝업을 열지 않는다. 중복 세션 팝업과 로그아웃 후 화면 잔류를 방지한다. 음성/대화는 아직 미연결이며 입력을 비활성화했다. 홀로그램은 대기 상태만 표시하고 가짜 발화 애니메이션을 사용하지 않는다. 저장된 시험 동작 결과가 있을 때만 횟수·점수·평균 품질을 표시한다.

CPU 시험 설정에서 기존 합성 카메라·녹화/재시작·종료 재시도·PWA 통합 검사가 통과했다. 팝업의 명시적 종료·다음/종료 선택·중복 방지·로그아웃 정리·390/1366 폭 및 두 테마 검사를 별도로 통과했다. 실제 사람 동작이나 무료 AI 연결 검증은 아니다.
