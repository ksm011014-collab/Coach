목표 모드로 아래 목표를 등록하고, 계획에서 멈추지 말고 프론트엔드 구현과 검증까지 진행해줘.

목표:
BoxingCoach의 프론트엔드를 먼저 완성한다.
기존 코드와 CSS를 정리하고, 실제 체육관 운영에 필요한 관리 화면 및 사용자 흐름을 구현한다. 신규 기능은 개발용 데이터로 동작을 확인할 수 있게 만들고, 추후 백엔드를 연결하기 쉬운 구조로 준비한다.

이번 목표의 완료는 “프론트엔드 완성”이다.
신규 DB·API·결제·알림 서비스를 구현하거나 실제 운영 기능이 완성됐다고 보고하지 않는다.

1\. 프로젝트 확인

\- AGENTS.md와 하위 지침을 읽는다.
\- box/docs/refoundation/의 제거·백엔드·장치 계약 문서가 있으면 확인한다.
\- 현재 코드, API 연결, Git 변경 상태, 관련 테스트를 확인한다.
\- 이전 대화에서 지적한 문제도 현재 코드에서 재확인한다.
\- 기존 사용자 변경과 실제 데이터는 보존한다.
\- 통상적인 레이아웃·컴포넌트 구현은 스스로 판단하고 진행한다.
\- 사용 가능한 범위에서 주요 화면의 변경 전 상태를 확보한다.

2\. 디자인 방향

\- 기존 APEX 브랜드, 어두운 배경, 청록색 네온, HUD 계열의 인상을 유지한다.
\- 실제 체육관 직원이 매일 쓰는 관리 프로그램답게 읽기 쉽고 단정하게 만든다.
\- 불필요한 여백, 내용 없는 고정 높이, 빈 그리드 열, 중첩 카드, 과도한 테두리·광원을 줄인다.
\- 여백을 모두 없애거나 정보를 과밀하게 배치하지 않는다.
\- 긴 표는 넓게, 설정 폼은 적절한 최대 너비로 구성한다.
\- 제목·검색·필터·주요 버튼·표·상세 패널의 위치를 일관되게 만든다.
\- 주요 작업 버튼은 찾기 쉬운 곳에 두고, 삭제 등 위험한 동작은 구분한다.
\- 기존 라이트 테마가 있다면 함께 유지한다.
\- 새로운 브랜드나 프레임워크를 도입하지 않는다.

3\. 코드와 CSS 정리

\- 바닐라 HTML·CSS·JavaScript 구조를 유지한다.
\- CSS 중복, 미사용 선택자, 누적 덮어쓰기, 폐기된 기능의 참조를 정리한다.
\- 색상, 간격, 글자 크기, 반경, 테두리, 그림자를 공통 토큰으로 정리한다.
\- CSS는 역할과 화면별로 적절히 분리한다. 특정 줄 수나 파일 수를 억지로 맞추지 않는다.
\- 버튼, 폼, 표, 배지, 탭, 모달, 상세 패널, 페이지 이동, 알림, 빈 상태를 필요한 만큼 공통화한다.
\- 대형 렌더링 함수를 분리하고 이벤트 중복 등록과 입력 중 포커스 손실을 점검한다.
\- 동적 HTML 값의 이스케이프와 DOM 삽입 안전성을 점검한다.
\- 변경된 정적 파일 경로를 웹 서버, PWA 캐시, Windows/Android 패키징에 반영한다.
\- 생성 산출물을 소스처럼 직접 수정하지 않는다.

4\. 구현할 화면과 사용자 흐름

실시간 세션 화면은 이번 디자인 개편 대상에서 제외한다.
기존 세션·카메라·녹화 기능은 공통 스타일 변경으로 깨지지 않도록 회귀 확인만 한다.

A. 관리자 대시보드
\- 오늘 출석, 유효 회원권 보유 회원, 만료 예정, 이번 달 수납 요약
\- 오늘 출석 회원 목록
\- 만료 예정·장기 미방문·미납 확인 목록
\- 최근 등록·재등록·수납 활동
\- 요약을 누르면 해당 필터가 적용된 상세 화면으로 이동
\- 각 지표의 기간과 집계 기준 표시
\- 장식용 차트보다 실제 확인과 행동으로 이어지는 정보 우선

B. 회원 관리 및 회원 상세
\- 이름·연락처 검색, 상태 필터, 정렬, 페이지 이동
\- 회원 등록·수정
\- 회원을 선택하면 상세 화면 또는 패널 표시
\- 상세 탭:
&#x20; · 기본 정보
&#x20; · 회원권
&#x20; · 출석·운동 기록
&#x20; · 수납
&#x20; · 상담·코치 메모
\- 회원권 상태와 로그인 계정 상태를 구분
\- 메모는 작성자·작성 시각·내용을 표시
\- 기존에 실제 저장되는 회원 기능은 유지

C. 회원권 관리
\- 기간권·횟수권·체험권 상품 목록과 등록·수정 폼
\- 회원에게 이용권 부여
\- 시작일·만료일·잔여 횟수·상태 표시
\- 휴회·재개·연장·해지의 입력·확인·결과 흐름
\- 변경 사유와 이력 표시
\- 복잡한 환불·양도·자동 갱신 정책은 이번에 확정하거나 구현하지 않음

D. 출석 관리
\- 오늘 출석 목록과 회원 검색
\- 수동 출석 처리 및 취소 흐름

\- 월 이동 가능한 달력과 선택 날짜 상세
\- 방문 출석과 앱 운동 세션을 별도 데이터로 표현
\- QR·얼굴인식·출입문 장치 연동은 구현하지 않음

E. 수납 관리
\- 수납 목록, 기간·회원·결제 상태 필터
\- 결제 수단, 상품, 금액, 수납일, 미납 표시
\- 수납 등록과 취소·환불 내역 입력 화면
\- 예상 매출과 실제 수납을 구분
\- PG 결제, 자동 청구, 실제 환불 처리는 구현하지 않음
\- 법적·회계적 환불 계산 규칙을 임의로 만들지 않음

F. 운동 기록
\- 기존 실제 운동 기록 조회 유지
\- 기간·회원·완료 상태 필터와 정렬·페이지 이동
\- 기록 상세 및 기존 녹화 조회 동선 정리
\- 모션 점수나 AI 피드백을 새로 생성하지 않음

G. 회원용 화면
\- 내 이용권, 잔여 횟수, 최근 출석, 운동 기록 요약
\- 출석·운동 기록의 구분
\- 내 수납 내역
\- 프로필 수정 화면 정돈
\- 설정되지 않은 주간 목표를 사용자 목표처럼 표시하지 않음

H. 센터·직원·계정·설정
\- 기존 화면의 레이아웃과 정보 계층 정리
\- 센터 기본 정보와 운영 요약의 중복 축소
\- 직원 프로필과 로그인 계정 권한의 차이 표시
\- 역할·계정 상태 검색과 필터 보강
\- 설정은 짧고 일관된 행 또는 섹션으로 구성
\- 기존에 실제 적용되는 권한 규칙을 유지

수업 예약, 상담 영업 파이프라인, 공지 발송, 전자계약서,
챗봇, 중앙관제 확장은 이번 범위에 포함하지 않는다.
미구현 메뉴를 늘리기 위해 빈 화면을 추가하지 않는다.

5\. 실제 데이터와 개발용 데이터 분리

\- 현재 실제 API로 동작하는 기능은 그대로 유지한다.
\- 신규 기능은 명시적인 개발용 미리보기 모드에서 샘플 데이터로 구현한다.
\- 운영 모드에서는 신규 미연결 기능의 저장을 차단하고 연결 준비 중임을 안내한다.
\- 미리보기 모드는 기본적으로 꺼져 있어야 하며 활성화 방법을 문서화한다.
\- 미리보기에는 지속적으로 보이는 “개발용 샘플 데이터” 표시를 둔다.
\- 샘플 데이터는 고정된 합성 데이터를 사용한다.
\- 날짜에 의존하는 시나리오는 기준 날짜를 제어해 재현 가능하게 만든다.
\- 샘플 데이터와 실제 데이터를 한 목록이나 집계에 섞지 않는다.
\- 미리보기의 등록·수정·취소는 개발용 데이터 저장소에만 반영한다.
\- 기존 인증·회원·운동 기록·localStorage 키를 덮어쓰지 않는다.
\- 초기화가 필요하면 개발용 데이터만 초기화한다.
\- 실제 운영용 임의 출석·가상 직원·가짜 회원권 상태는 제거하거나 명확히 격리한다.
\- 화면을 채우는 샘플 데이터와 향후 AI 분석 결과를 혼동하지 않는다.
&#x20; 가짜 모션인식·점수·자동 피드백은 만들지 않는다.

6\. 백엔드 연결을 위한 구조

\- 화면에서 샘플 배열이나 저장소를 직접 조작하지 않도록 한다.
\- 기존 데이터 계층을 우선 재사용하고, 필요한 서비스 경계만 추가한다.
&#x20; 예: 회원권, 출석, 수납, 메모 조회·변경 서비스.
\- 개발용 구현도 비동기 인터페이스를 사용해 실제 API로 교체하기 쉽게 한다.
\- 모든 신규 변경 요청에 대해 로딩·성공·실패·중복 제출 방지를 구현한다.
\- 필요한 필드, ID, 날짜·시간 단위, 금액 단위, 상태값, 페이지 이동,
&#x20; 오류 응답, 센터·회원 관계를 문서화한다.
\- 권한이나 center\_id를 프론트 값만으로 신뢰해서는 안 된다는 점을 계약에 명시한다.
\- 휴회 시 기간 계산, 횟수 차감 시점, 미방문 기준 등 정책이 필요한 부분은
&#x20; 미리보기용 가정과 추후 확정할 정책을 구분한다.
\- 신규 서버 API나 DB 테이블은 만들지 않는다.
\- 기존 API와 충돌하는 경우 임의로 계약을 바꾸지 말고 프론트 범위에서 해결한다.

7\. 상태와 접근성

각 신규 주요 화면에서 다음을 확인한다.
\- 데이터 있음
\- 데이터 없음
\- 검색 결과 없음
\- 로딩
\- 조회 실패 및 재시도
\- 저장 실패와 입력 보존
\- 권한 부족
\- 긴 이름·긴 목록·많은 기록

키보드 이동, 포커스 표시, 폼 레이블, 모달 포커스 복귀,
오류 안내, 대비, prefers-reduced-motion을 점검한다.
모바일에서 표를 무조건 압축하지 말고 가로 스크롤 또는 요약형 표시를 사용한다.

8\. 검증

\- 기존 관련 테스트를 먼저 실행해 기준 상태를 확인한다.
\- 변경한 사용자 흐름과 데이터 격리에 필요한 의미 있는 테스트를 추가한다.
\- 샘플 데이터로 실제 등록·수정·휴회·출석·수납·필터·상세 이동을 확인한다.
\- 실패 시 성공 메시지가 뜨지 않는지, 중복 클릭으로 중복 생성되지 않는지 확인한다.
\- 1920×1080, 1366×768, 모바일 크기에서 잘림과 겹침을 점검한다.
\- 다크·라이트 테마와 관리자·코치·회원 역할을 확인한다.
\- 개발용 모드가 실제 API 변경 요청을 보내거나 실제 저장소를 오염시키지 않는지 검증한다.
\- 브라우저 검증과 실제 WebView2/Android 검증은 구분한다.
\- 실행하지 못한 환경은 미검증으로 남긴다.
\- 테스트 실패를 숨기기 위해 기존 검증을 삭제하거나 약화하지 않는다.

9\. 완료 조건

\- 범위에 포함된 화면과 주요 사용자 흐름을 프론트에서 확인할 수 있다.
\- 기존 스타일을 유지하면서 빈 공간·배치·정보 우선순위가 개선된다.
\- 기존 실제 연결 기능이 유지된다.
\- 신규 기능은 개발용 모드에서 동작하고 운영 모드와 격리된다.
\- 버튼만 있고 반응이 없거나 저장 성공을 가장하는 동작이 없다.
\- CSS·컴포넌트·데이터 접근 구조가 정리된다.
\- 다음 작업자가 백엔드 구현을 시작할 수 있는 계약과 기능별 연결 목록이 있다.

10\. 인수인계

box/docs/refoundation/에 기존 문서와 충돌하지 않는 이름으로
프론트 구현 보고서와 백엔드 연결 명세를 작성한다.

\- 화면별 구현 내용
\- 개발용 미리보기 실행·초기화 방법
\- 실제 연결 / 개발용 동작 / 미연결 기능 목록
\- 파일과 컴포넌트 구조
\- 필요한 데이터 모델과 API 계약 초안
\- 확정되지 않은 업무 정책
\- 검증 결과와 미검증 환경

커밋·푸시·배포, 운영 데이터 변경, 기존 DB·녹화 삭제는 하지 않는다.
영어·한국어 챗봇 → 중앙관제 → 서버 구축 → 기록 조회 앱은
향후 방향으로만 기록하고 이번 작업을 확장하는 근거로 사용하지 않는다.
